Guide du projet : assistant d'étude

Ce document explique le dépôt E-learning : ce qu'on construit, comment c'est organisé, à quoi sert chaque dossier et chaque fichier, et les outils utilisés. Les noms de fichiers, de fonctions et de commandes sont écrits exactement comme dans le dépôt.

Phase 0 : code terminé, 31 tests OK Phase 0 : 2 vérifications avec la vraie clé API à faire Interface étudiante : démo cliquable Phases 1 à 8 : à faire

1. Le projet en bref

On construit un assistant d'étude du style NotebookLM pour la plateforme E-learning. L'étudiant dépose ses documents de cours et l'assistant l'aide à réviser.

Ce qu'on dépose

PDF (numériques, scannés, ou avec du texte dans des images), photos (tableau, notes manuscrites), TXT, Markdown, DOCX, PPTX, enregistrements audio du prof. En français ou en anglais.

Chat avec citations

Des réponses tirées uniquement des documents, avec la source (fichier, page ou minute de l'audio). Si l'info n'y est pas, l'assistant le dit.

Résumé d'examen vérifié

Définitions et formules citées mot pour mot, vérifiées par du code et par un second modèle, puis insérées par le code (jamais recopiées par l'IA).

Podcast

Deux voix (un élève, un tuteur) qui résument le cours, à partir du contenu vérifié uniquement.

Apprentissage

Quiz, flashcards, niveau de maîtrise par notion, mode tuteur, plan de révision jusqu'à la date de l'examen.

Contraintes

Modèles d'IA gratuits de NVIDIA Build ; Python 3.13 ; tout doit rester rapide malgré les limites de requêtes (parallélisme, cache, reprise après crash).

Deux interfaces

Interface développeur : assistant/app/streamlit_app.py

Pour tester chaque étape : données de débogage, métriques, file des tâches de fond. Adresse : http://localhost:8501.

Interface étudiante : assistant/app/student_app.py

Le produit tel que l'étudiant le verra (Sources · Discussion · Studio), montré au professeur pour validation. Adresse : http://localhost:8502.

Règle du projetChaque fonctionnalité doit marcher dans les deux interfaces. L'interface étudiante lit toutes ses données via assistant/app/student_backend.py : aujourd'hui ce sont des données d'exemple ; chaque phase remplace une fonction par le vrai traitement, sans changer l'écran.

3. Architecture générale

Le code est organisé en couches. Les interfaces ne parlent jamais directement aux modèles : elles passent par assistant/core, qui gère le cache, les limites de requêtes et la base de données.

Les flèches montrent qui appelle qui. L'interface développeur dépose des tâches dans SQLite ; le worker les prend et les exécute ; tous les appels aux modèles passent par providers/, qui utilise le cache et le limiteur de runtime/.

Les grands principes

Un seul chemin vers les modèles

Tout appel à NVIDIA passe par core/providers/. Changer de modèle = changer config.yaml, pas le code.

Ne jamais payer deux fois

Chaque réponse de modèle est gardée en cache dans SQLite. Refaire le même appel est instantané et gratuit.

Respecter les limites

Le service gratuit accepte environ 35 à 40 requêtes par minute et par modèle. Le limiteur répartit les appels pour ne pas les dépasser.

Le travail long en arrière-plan

Le worker exécute les tâches longues. L'interface reste fluide et affiche la progression.

Reprise après crash

Chaque petite tâche enregistre son résultat dès qu'elle finit. Après un arrêt, seules les tâches inachevées sont refaites.

Vérifier, pas faire confiance

Ce que l'étudiant apprend (définitions, formules, réponses de quiz) est vérifié par du code puis par un second modèle.

4. Comment ça circule

Une tâche de fond (exemple : le « demo job » de la phase 0)

1
Clic dans l'interfaceonglet Performance → get_queue().enqueue("demo", …) ajoute une ligne dans la table jobs
2
Le worker la prendclaim() : une seule requête SQL atomique, deux workers ne prennent jamais la même
3
Découpage en tâchesJobContext.run_tasks() crée une ligne par tâche dans tasks
4
Appels en parallèlechaque tâche attend une place via limiter.slot(role), puis appelle le modèle (cache d'abord)
5
Résultat enregistrétask_done() sauve le résultat ; en cas d'erreur task_failed(), les autres continuent
6
Progression affichéejob_progress() calcule fait/total et le temps restant ; l'interface se rafraîchit toutes les 2 s

Une question dans le chat (aujourd'hui, interface étudiante)

1
Questionstudent_app.py appelle backend.answer(...)
2
Sources numérotéesles sources cochées sont mises dans le message, numérotées [1], [2]…
3
Modèle (si clé API)llm.stream() envoie au modèle « chat » avec la consigne : répondre seulement avec les sources et citer [n]
4
Affichage progressifles mots apparaissent au fur et à mesure ; sans clé API : réponse préparée
5
Citationsle texte est relu pour trouver les [n] ; chaque citation devient un bouton qui montre la source
À partir de la phase 1Au lieu de mettre toutes les sources dans le message, on cherchera les passages pertinents dans Qdrant (recherche par le sens + par les mots), on les reclassera avec le reranker, puis on enverra seulement les meilleurs au modèle. C'est le principe du RAG (voir le lexique).

assistant/ racine du code Python
assistant/__init__.py vide

Fichier vide qui fait de assistant un paquet Python, pour pouvoir écrire from assistant.core import …. Tous les __init__.py vides du projet ont ce même rôle.

assistant/config.yaml configuration

Tous les réglages, jamais écrits dans le code :

  • models : un rôle par usage (chat, fast, embed, rerank) avec l'identifiant du modèle NVIDIA, les modèles de secours, la limite de requêtes par minute (rpm) et le nombre d'appels simultanés (max_in_flight) ;
  • limits.background_share : 80 % du débit pour le worker, 20 % pour l'interface ;
  • nvidia (adresses de l'API), qdrant, cache, worker, paths.
Pourquoi des rôles ? Le code demande « le modèle chat », pas un nom précis : on change de modèle dans ce fichier seulement.
assistant/.env.example modèle

Modèle du fichier secret. On le copie en .env à la racine et on y met sa clé NVIDIA_API_KEY. Le vrai .env n'est jamais dans Git.

assistant/requirements.txt dépendances

La liste des bibliothèques nécessaires, avec des versions minimales (streamlit, openai, pydantic, qdrant-client, tenacity, aiolimiter, pytest…).

assistant/requirements.lock.txt dépendances

Les versions exactes installées (produit par pip freeze). On installe à partir de ce fichier pour que tout le monde ait exactement les mêmes versions.

assistant/worker.py processus

Le worker : un programme qui tourne en continu (python -m assistant.worker) et exécute les tâches de fond.

  • main() : au démarrage, initialise la base, remet en file les tâches abandonnées (requeue_stale), puis boucle : prend une tâche (claim), la lance, recommence ;
  • run_job() : trouve le bon handler, l'exécute, marque la tâche terminée ou en échec ;
  • _heartbeats() : signale toutes les 15 s que le worker est vivant ;
  • à l'arrêt (Ctrl+C) : remet ses tâches en cours dans la file (requeue_worker).
assistant/core/ base commune
core/config.py

Lit config.yaml et le fichier .env. get_settings() renvoie un objet Settings (mis en cache) avec :

  • model(role) : la config d'un rôle de modèle (ModelCfg) ;
  • api_key : la clé, avec un message d'erreur clair si elle manque ;
  • data_dir et qdrant_url : modifiables par les variables d'environnement ASSISTANT_DATA_DIR et QDRANT_URL (utilisées par les tests et par Docker).
core/db.py

Accès à SQLite (data/app.db) :

  • connect() : une connexion par fil d'exécution, en mode WAL (le worker écrit pendant que l'interface lit) ;
  • init_db() : applique dans l'ordre les fichiers de migrations/ pas encore appliqués ;
  • now() : l'heure actuelle au format ISO.
core/migrations/001_runtime.sql

Crée les tables de la phase 0 :

  • notebooks : les cahiers (un par matière) ;
  • jobs : les tâches de fond (type, paramètres, statut, worker, heartbeat) ;
  • tasks : les sous-tâches d'un job, avec leur résultat (permet la reprise) ;
  • call_cache : le cache des appels aux modèles ;
  • metrics : les mesures de temps et de consommation.
Règle : on n'édite jamais une migration déjà appliquée ; on en ajoute une nouvelle (002_…).
core/models.py

Les types de données partagés (classes Pydantic), définis dès maintenant pour que toutes les phases s'accordent : Block (un morceau de document : titre, paragraphe, tableau, formule…), PageReport, DocumentIR (le document extrait, même format pour PDF, image, audio…), Chunk (un passage indexé), Citation.

core/notebooks.py

Créer, lister et retrouver un cahier : create_notebook(), list_notebooks(), get_notebook().

core/handlers/__init__.py

Importe tous les handlers pour qu'ils s'enregistrent. Chaque phase ajoutera ici son module (par exemple l'ingestion de fichiers en phase 1).

core/handlers/demo.py

La tâche de démonstration demo : lance N petites tâches, soit de vrais appels au modèle fast, soit des tâches factices (fake) qui attendent un peu. Sert à vérifier le parallélisme, les limites, la progression, la reprise et le cache.

assistant/core/providers/ les appels aux modèles
providers/base.py

La plomberie commune :

  • openai_client(), http_client() : un client par boucle d'exécution ;
  • with_retries() : réessaie avec une attente croissante si l'API répond 429 (trop de requêtes), 5xx, délai dépassé ou coupure ; pas sur une erreur 400 (notre faute) ;
  • with_fallbacks() : si le modèle principal est indisponible, essaie les modèles de secours de la config.
providers/llm.py

Les modèles de langage :

  • chat() : une réponse texte (avec cache) ;
  • chat_json() : une réponse JSON vérifiée par un schéma Pydantic, avec une tentative de réparation si le JSON est invalide ;
  • stream() : la réponse mot par mot (pour le chat), sans cache ;
  • strip_think() : enlève le « raisonnement » <think>…</think> que certains modèles écrivent ;
  • system_prefix : ajoute /no_think au modèle Nemotron pour couper ce raisonnement.
providers/embeddings.py

Transforme des textes en vecteurs : embed_passages() (documents, par lots de 32), embed_query() (une question), embedding_dim(). Chaque texte est mis en cache séparément : seuls les nouveaux textes sont envoyés.

Pourquoi pas de modèle de secours ici ? Des vecteurs de deux modèles différents ne sont pas comparables : on ne peut pas les mélanger.
providers/rerank.py

rerank(question, passages) : demande au reranker de NVIDIA de reclasser des passages du plus pertinent au moins pertinent. Renvoie des RerankHit (position + score).

assistant/core/runtime/ l'exécution : cache, limites, tâches
runtime/cache.py

Le cache des appels : make_key() calcule une empreinte SHA-256 de (type, modèle, version, entrée) ; cached_call() renvoie le résultat déjà connu ou exécute l'appel puis le stocke dans call_cache. cache_stats() pour l'affichage.

runtime/limiter.py

Le limiteur de requêtes : slot(role) attend une place libre (limite par minute + nombre d'appels simultanés). configure("worker" | "ui") donne 80 % du débit au worker et 20 % à l'interface, pour que le chat reste rapide pendant un traitement long.

runtime/queue.py

La file des tâches dans SQLite :

  • SqliteJobQueue : enqueue, claim (prise atomique), heartbeat, complete, fail, cancel, retry, requeue_stale (tâches d'un worker mort), requeue_worker, get, list ;
  • fonctions des sous-tâches : ensure_tasks, pending_tasks, task_started, task_done, task_failed, task_results.
runtime/jobs.py

Le registre des handlers (@handler("nom")) et JobContext.run_tasks() : enregistre les sous-tâches, exécute en parallèle celles qui ne sont pas finies, enregistre chaque résultat, et s'arrête si le job est annulé (JobCancelled).

runtime/progress.py

job_progress() renvoie un JobProgress (total, fait, échoué, en cours, étape, temps restant estimé). Le temps restant est calculé à partir du débit de la dernière minute.

runtime/metrics.py

Mesures : record() (gardées en mémoire puis écrites par lots), timer (chronomètre), summary() (nombre d'appels, temps médian p50 et p95, taux de cache, erreurs, 429 par étape et par modèle).

runtime/aio.py

Le pont entre Streamlit (synchrone) et les appels asynchrones : une boucle d'exécution tourne en permanence dans un fil séparé ; run_sync() attend un résultat, iter_sync() transforme un flux asynchrone en flux normal (pour afficher le chat mot par mot).

7. Concepts clés du code

Job et tâches

Un job = un travail demandé (« analyser ce PDF »). Il est découpé en tâches (« page 12 »). Chaque tâche enregistre son résultat dès qu'elle finit.

Handler

La fonction qui sait exécuter un type de job. On l'enregistre avec @handler("demo") ; le worker la retrouve par son nom.

Heartbeat

Le « battement de cœur » : le worker met à jour heartbeat_at toutes les 15 s. Sans battement depuis 2 min, on considère le worker mort et on remet ses jobs en file.

Rôle de modèle

chat (qualité), fast (rapide, gros volumes), embed (vecteurs), rerank (reclassement). Le code demande un rôle, la config dit quel modèle l'occupe.

Modèle de secours (fallback)

Si le modèle principal ne répond plus après plusieurs essais, on passe au suivant de la liste fallbacks.

Réessai avec attente croissante

Après une erreur temporaire, on attend un peu, puis plus longtemps, jusqu'à 5 essais (bibliothèque tenacity).

Migration

Un fichier SQL numéroté qui fait évoluer la base. init_db() applique ceux qui manquent, dans l'ordre.

Mode démo

Sans clé API, l'interface étudiante utilise des réponses préparées pour rester présentable.

L'éditeur de code. Avec l'extension Python, il active le venv automatiquement grâce à .vscode/settings.json.

YAML (.yaml)

Un format de fichier de réglages lisible par un humain (indentation, clé: valeur). Utilisé pour config.yaml et docker-compose.yml.

.env

Un fichier de variables secrètes (la clé API). Jamais envoyé sur GitHub ni dans une image Docker.

Markdown (.md)

Du texte simple avec une mise en forme légère (# titres, - listes). Toute la documentation est en Markdown.

Docker

Docker

Un outil qui fait tourner des programmes dans des conteneurs : des boîtes isolées qui contiennent le programme et tout ce dont il a besoin. Le programme marche pareil sur tous les ordinateurs.

Image

Le « modèle » figé d'un conteneur (système + Python + bibliothèques + code). Exemples : qdrant/qdrant:v1.15.5, elearning-assistant:dev.

Conteneur

Une image en train de tourner. On peut en lancer plusieurs à partir de la même image (ici : worker, ui, student).

Dockerfile

La recette pour construire une image, ligne par ligne (FROM, COPY, RUN, CMD).

Docker Compose

Lance plusieurs conteneurs ensemble à partir d'un seul fichier, docker-compose.yml. Une commande : docker compose up -d.

Volume

Un espace de stockage géré par Docker qui garde les données même si le conteneur est supprimé (qdrant_storage, app_data).

Port

Une « porte » d'accès réseau. 8502:8502 rend le conteneur accessible à http://localhost:8502.

Profil Compose

Un groupe de services lancé seulement sur demande. Ici --profile app ajoute le worker et les deux interfaces à Qdrant.

Données et recherche

SQLite

Une base de données SQL contenue dans un seul fichier (data/app.db), sans serveur. Elle garde cahiers, tâches, cache et métriques.

Mode WAL : permet d'écrire et de lire en même temps (le worker écrit, l'interface lit).

Qdrant

Une base de données vectorielle. Elle range les passages des documents sous forme de vecteurs et retrouve très vite ceux qui ont un sens proche d'une question. Elle sait aussi chercher par mots-clés (BM25) et filtrer par cahier.

Tableau de bord : http://localhost:6333/dashboard. Utilisée à partir de la phase 1.

Vecteur / embedding

Une liste de nombres qui représente le sens d'un texte. Deux textes de sens proche ont des vecteurs proches, même en deux langues différentes : « photosynthèse » et « photosynthesis ».

Reranker

Un modèle qui relit une question et une liste de passages et les reclasse du plus pertinent au moins pertinent. Plus précis que la recherche seule.

Redis

Une base en mémoire, très rapide, pour partager une file de tâches entre plusieurs machines. Pas utilisée maintenant ; prévue en phase 8 pour la production.

Cache

Une mémoire des résultats déjà calculés. Si on refait le même appel, on reprend le résultat au lieu de rappeler le modèle.

Intelligence artificielle

LLM (grand modèle de langage)

Un modèle d'IA entraîné sur énormément de texte, capable de comprendre une consigne et de rédiger une réponse. Il peut se tromper ou « inventer » (halluciner) : c'est pour ça qu'on l'oblige à citer ses sources et qu'on vérifie.

NVIDIA Build

Le site (build.nvidia.com) qui donne accès gratuitement à de nombreux modèles d'IA par Internet, avec une clé API. Gratuit mais limité (environ 40 requêtes par minute et par modèle) et prévu pour le développement.

API et clé API

Une API est une façon pour un programme d'en appeler un autre par Internet. La clé API (nvapi-…) prouve qui appelle ; elle est secrète.

Modèles utilisés (rôles)

chat : Nemotron Super 49B (réponses de qualité) ; fast : Llama 3.1 8B (tâches nombreuses) ; embed : nv-embedqa (vecteurs, multilingue) ; rerank : nv-rerankqa. Les identifiants sont dans config.yaml.

RAG

Retrieval-Augmented Generation : avant de répondre, on cherche les passages utiles dans les documents, puis on demande au LLM de répondre uniquement à partir de ces passages, en les citant.

OCR

Reconnaissance de caractères : lire le texte contenu dans une image ou une page scannée (phases 1 et 3).

VLM

Modèle vision-langage : un LLM qui comprend aussi les images (schémas, écriture manuscrite, formules).

ASR / TTS

ASR : transformer la parole en texte (transcrire le cours audio, phase 4). TTS : transformer du texte en voix (podcast, phase 6).

Token

Un petit morceau de texte (environ ¾ de mot) : c'est l'unité que les modèles lisent et produisent.

Erreur 429

Réponse « trop de requêtes » de l'API : on a dépassé la limite. Le limiteur l'évite et le réessai la gère.

Bibliothèques Python

Streamlit

Crée une application web en Python, sans HTML ni JavaScript. Utilisé pour les deux interfaces.

openai (SDK)

La bibliothèque officielle pour appeler des modèles au format OpenAI. NVIDIA Build accepte ce format : on l'utilise avec l'adresse de NVIDIA.

Pydantic

Décrit la forme des données (classes avec types) et vérifie qu'une donnée la respecte. Sert pour la config, les modèles de données et le JSON des LLM.

asyncio

La programmation asynchrone de Python : lancer beaucoup d'appels réseau en même temps sans attendre chacun.

aiolimiter

Limite le nombre d'appels par minute en mode asynchrone (dans limiter.py).

tenacity

Gère les réessais automatiques avec attente croissante (dans base.py).

httpx

Client HTTP asynchrone, utilisé pour le reranker (qui n'a pas le format OpenAI).

qdrant-client

La bibliothèque Python pour parler à Qdrant.

pytest

L'outil de tests automatiques. pytest lance les 31 tests ; pytest -m live lance ceux qui appellent la vraie API.

pandas

Manipulation de tableaux de données ; utilisé pour afficher les tableaux dans Streamlit.

10. Questions probables du prof

Pourquoi le RAG et pas l'entraînement d'un modèle sur les cours ?

Entraîner un modèle coûte cher, prend du temps, et il peut quand même inventer. Avec le RAG, le modèle répond à partir des passages retrouvés et les cite : c'est vérifiable, à jour dès qu'on ajoute un document, et ça marche avec des modèles gratuits.

Comment évitez-vous que l'IA invente ?

Consigne de répondre seulement avec les sources et de citer [n] ; vérification que chaque citation existe ; réponse « pas dans tes documents » quand rien ne correspond (phase 2) ; pour le résumé, citations mot pour mot vérifiées par du code et un second modèle, et formules insérées par le code (phase 5).

Pourquoi Qdrant ?

Il combine recherche par le sens (vecteurs) et par mots-clés (BM25), filtre par cahier, tourne en local dans Docker et peut passer en serveur pour la production.

Pourquoi SQLite et pas Redis ?

Ils ne font pas le même travail. On a besoin de garder durablement des résultats coûteux (OCR, transcriptions) et des données reliées entre elles : c'est le rôle d'une base SQL. Avec un seul worker sur une machine, SQLite suffit. Redis sert à partager une file entre plusieurs machines : prévu en phase 8. Le code passe par des interfaces (JobQueue, CallCache) pour pouvoir changer facilement.

Pourquoi un worker séparé ?

Analyser un PDF de 200 pages ou une heure d'audio prend des minutes. Si l'interface le faisait elle-même, elle serait bloquée. Le worker travaille en arrière-plan, l'interface affiche la progression, et un crash ne perd pas le travail déjà fait.

Que se passe-t-il si l'API renvoie « trop de requêtes » (429) ?

D'abord, le limiteur évite de dépasser la limite. Si ça arrive quand même, with_retries réessaie avec une attente croissante (jusqu'à 5 fois). Si le modèle reste indisponible, with_fallbacks passe au modèle de secours.

Comment vérifiez-vous que la reprise après crash marche ?

Par un test automatique (test_run_tasks_resumes_only_unfinished) et par un vrai essai : worker arrêté de force après 3 tâches sur 300, puis relancé ; le job s'est terminé à 300/300 et les 3 tâches déjà faites n'ont pas été refaites.

Comment testez-vous sans payer d'appels ?

Les tests utilisent un faux client qui imite l'API (réponses, erreurs 429, 404, 400). Les tests qui appellent la vraie API sont marqués live et ne tournent que sur demande.

Pourquoi deux interfaces ?

L'interface développeur montre tout ce qui sert à déboguer (scores, prompts, métriques) ; l'interface étudiante montre seulement le produit, propre, pour valider l'expérience avec le professeur. Les deux utilisent le même cœur (assistant/core).

Pourquoi pas YOLO pour les images ?

YOLO détecte des objets (« une personne, une chaise ») mais ne lit pas le texte et ne comprend pas un schéma. Pour des documents d'étude, il faut de l'OCR et un modèle vision-langage.

Pourquoi le résumé n'utilise-t-il pas le RAG ?

Le RAG ne garde que les passages les plus pertinents pour une question : il en oublie volontairement. Un résumé doit être complet, donc on parcourt tout le cours section par section (map-reduce), puis on vérifie qu'aucun élément obligatoire ne manque.

Pourquoi des volumes Docker et pas un dossier du PC ?

Sous Windows, monter un dossier du disque dans un conteneur peut corrompre les fichiers de Qdrant et le journal WAL de SQLite. Les volumes nommés évitent ce problème.
